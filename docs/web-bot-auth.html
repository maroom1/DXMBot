Identity & Web Bot Auth

How Cairn identifies itself on every request, from the User-Agent token to Ed25519 HTTP Message Signatures (Web Bot Auth), and how a site owner can check cryptographically that traffic really comes from Cairn.

1. Identity layers

Cairn never hides who it is. Each request carries several independent identity signals. They get harder to forge as you go down the list. The first four can be checked by anyone. The fifth is the only one that proves the request came from whoever holds the Cairn operator's private key.

The three roles share one signing key (one operator, one identity). Each role has its own UA token and its own IP JSON file, just as OpenAI publishes searchbot.json, gptbot.json and chatgpt-user.json.

A site that only needs "is this Cairn-shaped traffic?" can stop at layer 1. Allowlisting or granting extra access should require layer 4 or layer 5.

2. Header formats

Cairn implements the IETF drafts draft-meunier-web-bot-auth-architecture (Web Bot Auth) and draft-meunier-http-message-signatures-directory, on top of RFC 9421 HTTP Message Signatures, using Ed25519. Signer.signRequest({method, url}) in src/net/signing.js returns three headers. The fetcher adds them to every outgoing request, including robots.txt requests, whenever config.signing.enabled is true (the default).

HeaderFormatNotes
Signature-Agent"<publicBaseUrl>": a Structured Field string (RFC 8941), including the double quotesTells the verifier where to find the key directory: <Signature-Agent>/.well-known/http-message-signatures-directory
Signature-Inputsig1=("@authority" "signature-agent");created=<s>;expires=<s+300>;keyid="<kid>";alg="ed25519";nonce="<b64>";tag="web-bot-auth"Label sig1. The covered components are the target authority and the Signature-Agent header. Signatures are valid for 5 minutes. nonce is fresh random bytes (base64) on every request.
Signaturesig1=:<base64 Ed25519 signature>:An RFC 8941 byte sequence (:…:) holding a 64-byte signature

Signature base (RFC 9421 §2.5)

The bytes that get signed are three lines joined with \n, with no trailing newline:

"@authority": <host[:port], lowercased, default port omitted>
"signature-agent": "<publicBaseUrl>"
"@signature-params": ("@authority" "signature-agent");created=…;expires=…;keyid="…";alg="ed25519";nonce="…";tag="web-bot-auth"

The signature-agent line holds the header's raw field value, so the quotes are part of the signed bytes. The @signature-params line is exactly the Signature-Input value with the leading sig1= removed.

Signing is stateless and costs microseconds. A new nonce and timestamp make every request's signature unique. When config.signing.enabled is false, signRequest returns {} and the audit entry records signed:false.

4. Key generation, storage and thumbprint

  • Generation. On the first Signer.init(), when no key exists, Cairn creates an Ed25519 key pair with crypto.generateKeyPairSync('ed25519'). There is no external tool and no npm dependency.
  • Storage. Keys are stored in <dataDir>/keys/. The private key is ed25519-private.pem (PEM, file mode 0600). The public key is ed25519-public.pem (PEM). Later runs load the same files, so the keyid stays the same across restarts.
  • Key id. signer.keyId is the RFC 7638 JWK thumbprint. It is the SHA-256 of the canonical JSON of the required public members, in lexicographic order and without whitespace, {"crv":"Ed25519","kty":"OKP","x":"<base64url public key>"}, encoded as base64url without padding. Because verifiers can recompute it from the JWK, a directory cannot claim a kid that does not belong to its key.
  • Rotation. Stop Cairn, move ed25519-*.pem out of the keys directory, and start again. A new pair and a new keyid are generated. The directory publishes only the current key, so old signatures stop verifying straight away.
  • Inspection. node bin/cairn.js keys prints the JWKS and keyid. GET /api/identity returns keyId and jwksUrl. POST /api/sign-preview shows the exact headers that would be sent for a URL.
import crypto from 'node:crypto';

export function jwkThumbprint(jwk) {
  // RFC 7638 §3.2: only the required members for kty "OKP", in lexicographic order.
  const canonical = JSON.stringify({ crv: jwk.crv, kty: jwk.kty, x: jwk.x });
  return crypto.createHash('sha256').update(canonical).digest('base64url');
}

6. Verification algorithm for site owners

This is what the fixture's /signed-only route and Cairn's own verifyRequest(...) do (POST /api/verify-signature exposes it). Any site can do the same with a few dozen lines of code.

  1. Require the headers. Signature-Input, Signature and Signature-Agent must all be present. If they are not, treat the request as unsigned. That is not an error, only unverified.
  2. Pick the Web Bot Auth signature. Parse Signature-Input as an RFC 8941 dictionary and select the label whose parameters include tag="web-bot-auth" (Cairn uses sig1).
  3. Check coverage. The component list must include "@authority", and "signature-agent" whenever that header is present. Otherwise an attacker could swap the directory URL.
  4. Check the time window. Require created ≤ now + skew (allow about 60 s of clock skew) and now < expires. Reject lifetimes longer than your policy allows (Cairn sends 300 s).
  5. Decide whether you trust the agent. Parse Signature-Agent (remove the SF-string quotes). Compare it with your allowlist of operators you recognise, and in production require https.
  6. Fetch the directory. GET <agent>/.well-known/http-message-signatures-directory. Cache it, respecting HTTP caching, so you do not fetch it for every request.
  7. Find the key. Pick the JWK with kty=OKP, crv=Ed25519 whose recomputed RFC 7638 thumbprint equals keyid.
  8. Rebuild the signature base from the request you actually received: @authority from your own view of the Host, lowercased and without the default port, the raw Signature-Agent value, and @signature-params.
  9. Verify the Ed25519 signature from the Signature header (sig1=:…:, base64) over the base bytes.
  10. Optional: prevent replay. Remember (keyid, nonce) pairs until expires and reject any repeat.
  11. Combine with the other layers: the UA token should match the role, and the source IP should appear in the role's /bot/*.json.

The key-directory fetch happens once per cache period, not once per request. Everything else is local CPU work.

Reference verifier (Node.js, zero dependencies)

import crypto from 'node:crypto';
import { jwkThumbprint } from './thumbprint.js';     // the function from section 4

const directoryCache = new Map();                    // agent URL -> { jwks, expiresAt }

async function loadDirectory(agent) {
  const hit = directoryCache.get(agent);
  if (hit && hit.expiresAt > Date.now()) return hit.jwks;
  const res = await fetch(new URL('/.well-known/http-message-signatures-directory', agent));
  if (!res.ok) throw new Error(`directory HTTP ${res.status}`);
  const jwks = await res.json();
  directoryCache.set(agent, { jwks, expiresAt: Date.now() + 3600_000 });
  return jwks;
}

// headers: lowercase-keyed; authority: the Host you served, e.g. "127.0.0.1:8788".
// Simplified: handles a single signature label, which is what Cairn sends.
export async function verifyWebBotAuth({ headers, authority }, { now = Date.now() / 1000, trustedAgents = [] } = {}) {
  const input = headers['signature-input'], sigHeader = headers['signature'], agentField = headers['signature-agent'];
  if (!input || !sigHeader || !agentField) return { valid: false, reason: 'unsigned' };

  const m = /^([A-Za-z0-9_-]+)=\(([^)]*)\)(.*)$/.exec(input);
  if (!m) return { valid: false, reason: 'malformed Signature-Input' };
  const [, label, list, paramText] = m;
  const components = [...list.matchAll(/"([^"]+)"/g)].map((x) => x[1]);
  const params = Object.fromEntries([...paramText.matchAll(/;([a-z]+)=(?:"([^"]*)"|(\d+))/g)]
    .map((x) => [x[1], x[2] ?? Number(x[3])]));

  if (params.tag !== 'web-bot-auth') return { valid: false, reason: 'not a web-bot-auth signature' };
  if (!components.includes('@authority') || !components.includes('signature-agent')) return { valid: false, reason: 'insufficient coverage' };
  if (!(params.created <= now + 60 && now < params.expires)) return { valid: false, reason: 'outside validity window' };

  const agent = agentField.replace(/^"|"$/g, '');
  if (trustedAgents.length && !trustedAgents.includes(agent)) return { valid: false, reason: 'untrusted agent' };
  const jwk = (await loadDirectory(agent)).keys
    .find((k) => k.kty === 'OKP' && k.crv === 'Ed25519' && jwkThumbprint(k) === params.keyid);
  if (!jwk) return { valid: false, reason: 'unknown keyid' };

  const base = [
    ...components.map((c) => (c === '@authority' ? `"@authority": ${authority.toLowerCase()}` : `"${c}": ${headers[c]}`)),
    `"@signature-params": ${input.slice(label.length + 1)}`,
  ].join('\n');
  const sig = new RegExp(`(?:^|,\\s*)${label}=:([^:]+):`).exec(sigHeader)?.[1];
  if (!sig) return { valid: false, reason: 'missing signature value' };

  const key = crypto.createPublicKey({ key: { kty: 'OKP', crv: 'Ed25519', x: jwk.x }, format: 'jwk' });
  const valid = crypto.verify(null, Buffer.from(base), key, Buffer.from(sig, 'base64'));
  return valid ? { valid: true, keyid: params.keyid, agent } : { valid: false, reason: 'bad signature' };
}
To try it locally, POST /api/verify-signature with {"url": "...", "headers": {...}} verifies a header set against this installation's JWKS. The Fetch inspector in the web UI shows the headers that were sent for any fetch.

7. Verified-bot programs (Cloudflare-style)

Most site owners will not verify signatures themselves. CDNs and bot-management vendors, with Cloudflare the most visible, run verified bot or signed agent programs that do it at the edge:

  1. Registration. The bot operator submits its details to the program: name, purpose, UA token, documentation URL (Cairn's /bot page) and the key directory URL (/.well-known/http-message-signatures-directory). The directory must be reachable on the public internet over HTTPS.
  2. Edge verification. For every request that carries Signature-Agent, the CDN fetches and caches the directory, verifies the signature as in section 6, and sets a "verified bot" attribute on the request.
  3. Customer policy. Site owners write rules against that attribute rather than against a spoofable UA string. For example: allow verified CairnSearch, challenge unverified traffic claiming to be Cairn, or rate-limit a category of bots.
  4. Revocation. If a key leaks, the operator rotates it, the directory changes, and the edge stops trusting the old keyid once its cached copy expires.

The site owner never handles keys. The CDN turns the signature into a single trusted "verified" flag that rules can use.

AI agent operators already sign this way. OpenAI's ChatGPT agent, for example, is publicly documented as sending Web Bot Auth signatures with a Signature-Agent that points at its own directory. Cairn follows the same pattern so that the same edge rules can work for it too.

8. Limitations and draft status

Web Bot Auth is still an Internet-Draft, not an RFC. Header names, the shape of Signature-Agent (later revisions discuss a structured-field dictionary instead of a bare string), the required components and the directory format may change. Cairn implements the profile described in this page and in SPEC.md. RFC 9421 (message signatures) and RFC 7638 (thumbprints), which it builds on, are stable.
