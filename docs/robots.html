1. Scope: who checks robots.txt, and when

Every HTTP request Cairn makes goes through one component, the Fetcher (src/net/fetcher.js). Before it sends a page request, the fetcher asks the RobotsCache (src/robots/cache.js) whether the URL is allowed for the role making the request. There are three roles and each has its own robots.txt token, so site owners can control each one separately.

RolePrimary tokenToken order used for group selectionRespects robots.txt
search: search indexerCairnSearchCairnSearch → Cairn → *Always
corpus: dataset collectorCairnCorpusCairnCorpus → Cairn → *Always
user: user-triggered fetchCairn-UserCairn-User → Cairn → *By default (config.robots.respectForUserFetch, default true)

The token list comes from robotsTokens(role) in src/identity.js, which returns [roleToken, 'Cairn']. * is the fallback used only when neither token has a group.

The only request that skips the robots check is the request for /robots.txt itself. It still carries Cairn's honest User-Agent, is rate-limited like any other request, is signed (when signing is enabled) and is written to the audit log with kind:'robots'. When fetch.blockPrivateNetworks is on, it is also screened like a page request (scheme, private address, DNS answers, every redirect hop); a refused robots.txt request counts as "unreachable" (status 0), never as "missing".

If an operator turns off respectForUserFetch, user-triggered fetches are still logged, with robots:'skipped', so the choice shows up in the audit log. Search and corpus crawls always obey robots.txt, and no setting changes that.

3. Group selection: CairnSearch → Cairn → *

RobotsTxt.selectGroup(tokens) tries each token in order. The first token with any matching group wins, and only that group's rules apply. A group matches a token when one of its User-agent values:

  • equals the token, ignoring case (cairnsearch matches CairnSearch), or
  • starts with the token followed by / (User-agent: CairnSearch/1.0 matches CairnSearch).

If several groups match the same token, their rules are merged into one rule set (RFC 9309 §2.2.1). If no token matches, all User-agent: * groups are merged and used. If there is no * group either, the result is null and everything is allowed.

A specific group replaces *; it does not add to it. If your file has a User-agent: CairnSearch group, CairnSearch ignores everything under User-agent: *. Rules you want CairnSearch to follow must be repeated in its own group. This is the same as Googlebot and RFC 9309. Examples 4 and 5 below show the effect.

4. Rule matching

RobotsTxt.isAllowed(tokens, urlOrPath) returns {allowed, rule, matchedAgent}. The steps are:

  1. Target string. The URL's path plus query (pathWithQuery). The fragment is never part of it. An empty path becomes /.
  2. /robots.txt is always allowed, even under Disallow: / or RobotsTxt.disallowAll().
  3. Percent-encoding normalization is applied to both the rule pattern and the target. Escapes for unreserved characters (A–Z a–z 0–9 - . _ ~) are decoded, so %7E becomes ~. All other escapes are kept, with their hex digits uppercased, so %2f becomes %2F. That means /%7Euser and /~user are the same, but /a%2Fb and /a/b are not.
  4. Patterns. A rule matches when it matches a prefix of the target. * matches any run of characters, including none. A trailing $ means the pattern must match all the way to the end of the target.
  5. Empty Disallow: lines are ignored. They mean "nothing is disallowed".
  6. Longest match wins. Among the matching rules, the one with the longest pattern (in octets) decides.
  7. Ties go to Allow. If an Allow and a Disallow of equal length both match, the URL is allowed (RFC 9309 §2.2.2).
  8. No matching rule means the URL is allowed.
// Condensed from src/robots/parser.js (illustrative)
function decide(group, target) {
  if (target === '/robots.txt' || target.startsWith('/robots.txt?')) return { allowed: true, rule: null };
  if (!group) return { allowed: true, rule: null };                  // no group selected
  const t = normalizePercent(target);
  let best = null;
  for (const rule of group.rules) {
    if (rule.type === 'disallow' && rule.path === '') continue;         // empty Disallow is a no-op
    if (!patternMatches(normalizePercent(rule.path), t)) continue;      // '*' wildcard, '$' end anchor
    const len = Buffer.byteLength(rule.path);
    if (!best || len > best.len || (len === best.len && rule.type === 'allow')) best = { rule, len };
  }
  return best ? { allowed: best.rule.type === 'allow', rule: best.rule } : { allowed: true, rule: null };
}

5. Crawl-delay and Sitemap

Crawl-delay

Crawl-delay is not part of RFC 9309, but many sites use it and Cairn honours it. crawlDelay(tokens) returns the value from the group that group selection picked (the same group that supplies the rules). The fetcher passes that value to the host scheduler as crawlDelaySec. The scheduler then spaces request starts to the same host at least this far apart:

gap = max(config.politeness.minDelayMs, crawlDelaySec × 1000)     // minDelayMs defaults to 1000 ms

So Crawl-delay: 10 means at most one request every 10 seconds. With no Crawl-delay, Cairn's default is one request per second per host, with at most one request in flight per host. Crawl jobs never add their own sleeps. All pacing comes from the scheduler, so the limit applies across concurrent jobs.

A very large Crawl-delay would park requests in the queue for hours or days, so Cairn caps what it will wait for at 300 seconds (MAX_CRAWL_DELAY_SEC in src/net/fetcher.js). Above that, the site is treated as disallowing the role:

Crawl-delay in the selected groupFetcher behaviourWhat callers see
absent, negative or not a numberIgnored; spacing is politeness.minDelayMs (1 s)—
0 … 300Requests to the host start at least max(minDelayMs, delay × 1000) apartNormal fetch
above 300Treated as disallow: nothing is requestedblocked.reason: "robots", blocked.rule: null, blocked.detail "Crawl-delay of 600 s in … exceeds Cairn's maximum of 300 s; treated as disallowed", blocked.robots.crawlDelayLimit: 300; audit robots:'disallowed'; crawl outcome blocked-robots

The over-limit block is a politeness refusal, not an opt-out, so a crawl does not remove a previously indexed copy because of it (only a real Disallow rule does). POST /api/robots/check reports the raw decision (allowed: true with crawlDelay: 600); the limit is applied by the fetcher.

Sitemap

Sitemap: lines are global and are returned in sitemaps[] whichever group they appear in. When a crawl starts, it seeds the frontier from these URLs. If useSitemaps is on, it also tries /sitemap.xml. Sitemap indexes are followed up to 3 levels deep, with at most 1,000 URLs in total. Listing a URL in a sitemap does not bypass robots.txt: every sitemap URL is checked like any other URL before it is fetched.

6. Status codes, caching and failures

Cached robots.txt files are keyed by origin (scheme + host + port). http://example.com, https://example.com and https://www.example.com are three separate origins, each with its own robots.txt. The file is fetched with the requesting role's User-Agent, using fetchRaw. That call follows up to 5 redirects and applies the normal rate limits, signing and audit logging.

Outcome of fetching /robots.txtWhat Cairn assumesHow long it is cachedsourceRFC 9309 basis

  • Stale copies. If a refresh fails with 429, 5xx or a network error, Cairn keeps using the last good robots.txt instead of dropping to allow-all. This is the conservative choice: a site in trouble keeps the restrictions it last published. RFC 9309 allows a crawler to assume no restrictions after 30 days of unreachability. Cairn never does that.
  • TTL read at use time, capped at 24 h. The cache reads config.robots.cacheTtlMs on every lookup, so a POST /api/config change applies without a restart. An entry expires at the earlier of its original expiry and fetchedAt + current TTL, so lowering the TTL shortens existing entries at once. Values above 24 h are clamped by the cache and rejected by POST /api/config (400 "robots.cacheTtlMs must be at most 86400000"). Failure results last min(TTL, 10 min).
  • Bounded. At most 2000 origins are cached; expired entries are evicted first, then the least recently refreshed.
  • Single-flight. If many requests for the same origin arrive at once (for example, a crawl with concurrency: 4), they share one in-flight robots.txt fetch. The file is never fetched twice in parallel.
  • Inspection and invalidation. GET /api/robots/cache lists cached entries: origin, status, fetchedAt, expiresAt, group count and sitemaps. POST /api/robots/cache/clear empties the cache so the next request re-fetches.

Successful results and 4xx results last for the configured TTL (24 hours by default, never longer). Failures are retried after at most 10 minutes. The last good copy is kept, and reused while the server keeps failing.

7. Redirects are re-checked on every hop

Cairn follows page redirects itself, one hop at a time (up to config.fetch.maxRedirects, default 5), rather than letting the HTTP client follow them automatically. Before following each Location, it runs the robots check again on the new URL. If the new URL is on a different origin, that origin's robots.txt is fetched or loaded from cache. A redirect into a disallowed area therefore stops at the redirect. The disallowed page is never requested.

Two audit entries are written: one for the 302 response, and one with blocked:'robots' and status: null for the refused hop.

The refusal describes the hop that was actually blocked, not the URL first requested. FetchResult.blocked for a robots block is:

FieldMeaning
reason"robots"
detailHuman-readable: Disallowed by <robotsUrl> (disallow: /private/), plus the synthetic-policy note when robots.txt was unreachable, or the Crawl-delay explanation
ruleThe matching rule, or null (synthetic disallow-all, Crawl-delay over 300 s)
robotsThe blocking hop's full decision: url (the hop), allowed: false, rule, matchedAgent, robotsUrl (the hop's origin), crawlDelay, status, source, fetchedAt, expiresAt, note (set for synthetic policies), and crawlDelayLimit: 300 for Crawl-delay blocks

POST /api/fetch returns this blocked.robots as its top-level robots field, so a redirect from a.example into a path disallowed by b.example/robots.txt is explained with b.example's rule. Crawls use robots.note and crawlDelayLimit to tell a real opt-out (drop any indexed copy) from a temporary or politeness block (keep it).

8. Page-level controls: meta robots and X-Robots-Tag

robots.txt decides whether Cairn may request a URL. Page-level directives decide what Cairn may do with a page it was allowed to fetch. Cairn reads them from two places and combines them. If any source sets a directive, it applies.

SourceFormApplies to
HTML meta, generic<meta name="robots" content="noindex, nofollow">All roles
HTML meta, bot-scoped<meta name="CairnSearch" content="noindex">Only the role whose token is named. name="Cairn" applies to every Cairn role. Names are matched case-insensitively.
HTTP header, genericX-Robots-Tag: noindexAll roles. Works for non-HTML responses too.
HTTP header, bot-scopedX-Robots-Tag: CairnSearch: noindexOnly the role whose token is named
Link-level<a href="…" rel="nofollow">That one link is not added to the crawl frontier

Supported values: noindex, nofollow, noarchive (also nocache), nosnippet (also max-snippet:0, with or without spaces around the colon), and none (the same as noindex, nofollow). Other values, including max-snippet with a non-zero value, are ignored. Directives scoped to other bots, such as googlebot: noindex, are ignored.

How X-Robots-Tag is parsed (fails closed)

HTTP clients join repeated X-Robots-Tag header lines with ", ". So X-Robots-Tag: otherbot: noindex followed by X-Robots-Tag: nofollow arrives as otherbot: noindex, nofollow, and it is impossible to tell whether nofollow continues otherbot's line or is a separate site-wide line. parseXRobotsTag therefore splits on commas and judges each part on its own; when in doubt it applies the restriction.
