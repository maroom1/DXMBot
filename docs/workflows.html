A crawl is a breadth-first walk seeded from the start URLs and from sitemaps. All waiting happens inside the fetcher's scheduler, so the crawler loop has no sleeps of its own.

  1. A job is created from the API or CLI. Its options default to config.crawl (maxPages 50, maxDepth 2, sameSiteOnly, useSitemaps, concurrency 4).
  2. Robots.txt is fetched once for each seed origin. Its Sitemap: lines and /sitemap.xml seed the frontier.
  3. Up to concurrency URLs are fetched at a time. Each fetch result is turned into exactly one outcome.
  4. Pages that can be indexed go to the search index (search role) or to a JSONL file (corpus role), never both.
  5. Links are followed unless the page is nofollow or the link has rel=nofollow. They must stay in scope (same site, include/exclude patterns) and under maxDepth.

All network access goes through this one pipeline. Robots.txt is checked before the first request and again on every redirect hop. Every attempt is scheduled per host, signed, and written to the audit log.

  1. The URL is normalised, and schemes other than http(s) are rejected (blocked.reason = 'scheme'). Private-network targets are rejected only if fetch.blockPrivateNetworks is set.
  2. The robots decision uses robotsTokens(role). For the user role it is skipped only when robots.respectForUserFetch is false.
  3. The scheduler enforces delay, concurrency and backoff. The signer adds Web Bot Auth headers when signing.enabled is true.
  4. The body is read up to maxBytes (and flagged truncated if cut) under an AbortController timeout. It is decoded using the charset when possible.
  5. Retryable failures are penalised and retried. Redirects are followed by hand so each hop can be checked (Figure 6).

3. robots.txt decision algorithm

RFC 9309 semantics: only one group applies. It is the most specific token that has any group, and a role-specific group completely replaces the * group rather than adding to it. Within that group, the longest matching pattern wins, and Allow wins a tie.

  1. Try the tokens in order: role token (CairnSearch, CairnCorpus or Cairn-User), then Cairn, then *.
  2. Match against the path plus query. Both sides are percent-normalised first.
  3. Among the rules that match, pick the one with the longest pattern. On equal length, Allow wins.
  4. If no rule matches, or no group applies, the URL is allowed.

  note right of Fetching
    One shared in-flight request per origin.
    Concurrent get() calls await the same promise.
  end note
  note left of Failed
    A server error is not permission.
    Cairn assumes full disallow
    until robots.txt is readable.
  end note
  note right of Expired
    TTL = robots.cacheTtlMs (default 24 h).
    invalidate(origin) or clear() returns
    any state to Absent.
  end note

The cache is keyed by origin (scheme, host and port). Failures are cached for no more than 10 minutes, so a site recovering from an outage is re-read quickly. A 4xx means "no robots.txt", which RFC 9309 treats as allow-all.

  1. The first get() for an origin fetches /robots.txt through fetchRaw with kind: 'robots', so the request is signed, rate-limited and audited.
  2. Each result records status, fetchedAt, expiresAt and a source of network, cache or stale.
  3. If the site answers 429 or 5xx, or the request fails, Cairn keeps the rules it already had. It never falls back to allow-all.
  4. Operators can force a re-read with POST /api/robots/cache/clear.

5. Politeness and backoff state machine

Figure 5 — HostScheduler per-host states
stateDiagram-v2
  state "Idle" as Idle
  state "Waiting (FIFO queue)" as Waiting
  state "In flight" as InFlight
  state "Backoff" as Backoff

  [*] --> Idle
  Idle --> Waiting : schedule(host, fn, crawlDelaySec)
  Waiting --> Waiting : before nextAllowedAt or backoffUntil
  Waiting --> InFlight : delay elapsed, host slot and global slot free
  InFlight --> Idle : fn settles, Fetcher calls reward(host)
  InFlight --> Backoff : 429, 503, 5xx or network error, penalize(host, retryAfterMs)
  Backoff --> Waiting : retry queued while backoffUntil is in the future
  Backoff --> Idle : backoffUntil passed with no queued work

  note right of Waiting
    nextAllowedAt = lastStart + max(minDelayMs, crawlDelaySec x 1000)
    The global slot is taken only after the host delay has elapsed.
  end note
  note right of Backoff
    backoff = min(backoffBaseMs x 2^n, maxBackoffMs)
    A larger Retry-After value wins.
    reward(host) resets n to 0.
  end note

Defaults: minDelayMs 1000, maxConcurrencyPerHost 1, globalConcurrency 8, backoffBaseMs 2000, maxBackoffMs 60000. A robots.txt Crawl-delay is respected whenever it is larger than the minimum delay.

  1. Requests for a host run in FIFO order. A request starts only once the host's delay and any backoff have passed.
  2. A slow host never blocks other hosts, because a request does not hold a global concurrency slot while it waits.
  3. Each consecutive failure doubles the backoff up to the cap. Retry-After (seconds or HTTP-date) can lengthen it further.
  4. stats() exposes inFlight, queued, backoffMs and nextAllowedAt per host, for /api/stats.

Redirects are never followed automatically. An open redirect on an allowed page cannot be used to reach a disallowed page. The demo site's /redirect-to-private (302 to /private/secret.html) is blocked, and the site never sees a request for the secret page.

  1. Every hop is recorded in FetchResult.redirects, which the Fetch inspector shows.
  2. A cross-origin hop loads that origin's robots.txt. Each origin's own rules apply to it.
  3. The per-hop check applies whenever respectRobots is in effect, which is always for the search and corpus roles and by default for the user role.
  4. fetchRaw (used for robots.txt itself) follows at most 5 redirects and does no robots check.

8. Crawl job states

Figure 8 — CrawlJob state diagram
stateDiagram-v2
  state "queued" as Queued
  state "done" as Done
  state "cancelled" as Cancelled
  state "error" as Errored

  [*] --> Queued : JobManager.create(opts)
  Queued --> Running : run() starts
  Queued --> Cancelled : cancel()
  state Running {
    state "Seed robots.txt" as SeedRobots
    state "Load sitemaps" as LoadSitemaps
    state "Crawl frontier" as CrawlFrontier
    [*] --> SeedRobots
    SeedRobots --> LoadSitemaps
    LoadSitemaps --> CrawlFrontier
    CrawlFrontier --> CrawlFrontier : fetch, classify, enqueue
    CrawlFrontier --> [*]
  }

  Running --> Cancelled : cancel(), no new fetches start
  Running --> Errored : unexpected exception
  Done --> [*]
  Cancelled --> [*]
  Errored --> [*]

A job's status().state is one of queued, running, done, cancelled or error. The terminal states are final. JobManager keeps the last 50 jobs, newest first.

  1. Each state change emits a state event with the full status. Each processed page emits a page event.
  2. Reaching a terminal state emits done. waitFor(id, timeoutMs) resolves on that event.
  3. After cancel(), no new fetches start. Fetches already in flight are allowed to finish or abort.
  4. If an exception escapes, the job ends in error with its message in status().error.

Only documents are saved to disk. Postings and passages are derived data, rebuilt by load() at startup. That keeps index.json small, readable and safe to write atomically.

  1. Extraction drops script, style, noscript, template, svg, iframe and head content, and honours <base href>.
  2. The tokenizer lowercases, keeps Unicode letters and digits, removes stopwords and applies light stemming (plural s, es and ies; ing; ed).
  3. If a page's text hash is unchanged, add() returns unchanged and nothing is rewritten.
  4. nosnippet documents return an empty snippet, and their text is never given to RAG.

Claude plans the research, but every page it reads is fetched by Cairn as Cairn-User, under the same robots.txt, rate limits and audit as any other fetch. A robots refusal comes back as an ordinary tool result, and the system prompt tells Claude to respect it and move on.

  1. Claude's built-in tools are disabled (--tools ''). Only the five mcp__cairn__* tools are allowed, and --strict-mcp-config excludes all other MCP servers.
  2. The system prompt says to search the index first, fetch pages only through tools, crawl small scopes (at most 25 pages, depth 2), and respect refusals.
  3. Each URL that surfaces gets a stable [n] id. The MCP server keeps CAIRN_SOURCES_FILE up to date after every change.
  4. Citations are the registry entries the final answer actually cites, in the order they are cited.
  5. If the Claude CLI is unavailable, deepResearch reports a status event and falls back to a quick answer (Figure 10) instead of failing.

The signature covers the target authority and the Signature-Agent URL. It proves that the request came from whoever controls the key published at that URL. The verifier needs no shared secret, only an HTTPS GET for the key directory.

Signature-Agent: "http://127.0.0.1:8787"
Signature-Input: sig1=("@authority" "signature-agent");created=1759240000;expires=1759240300;keyid="<jwk-thumbprint>";alg="ed25519";nonce="<base64>";tag="web-bot-auth"
Signature: sig1=:<base64 ed25519 signature>:

# signature base (RFC 9421 §2.5), lines joined by \n, no trailing newline
"@authority": example.com
"signature-agent": "http://127.0.0.1:8787"
"@signature-params": ("@authority" "signature-agent");created=1759240000;expires=1759240300;keyid="…";alg="ed25519";nonce="…";tag="web-bot-auth"
  1. The key pair is created once, and the private key is stored with mode 0600. The public key is published as a JWKS by the Cairn server.
  2. Every request, including each redirect hop and each robots.txt fetch, is signed afresh with a new nonce and a 300-second lifetime.
  3. Sites can verify with any RFC 9421 implementation. Operators can check headers locally with POST /api/verify-signature.
  4. Setting signing.enabled to false sends no signature headers. The honest User-Agent is still sent.

SSE uses plain text/event-stream over the same loopback connection. The dashboard needs no WebSocket or polling. On a failure the server emits an error event, and the stream ends with done. The audit feed at /api/audit/stream works the same way, with one entry event per audit record.

event: page
data: {"jobId":"job-1-mg2k9x","url":"http://127.0.0.1:8788/about.html","outcome":"indexed","status":200,"title":"About Northwind Trails","depth":1}

event: answer
data: {"answer":"The Ridgeback 45 weighs 1.2 kg [1] …","citations":[{"n":1,"url":"…","title":"…"}]}

event: done
data: {}
  1. Ask events: status, retrieval, tool, tool_result, text, answer, error, then done.
  2. Crawl events: page, state, done. The dashboard updates its counters and outcome table live.
  3. Event payloads are JSON. The UI renders them with DOM text nodes, never unescaped innerHTML.
  4. Closing the tab closes the EventSource. The server then unsubscribes its listeners.

An opt-out takes effect the next time robots.txt is read. That happens at most one TTL (24 hours by default) after the edit, or at once if the operator clears the cache. A robots.txt outage cannot silently undo an opt-out, because failures reuse the last good copy (Figure 4).

  1. The site owner learns the tokens from the /bot page or from the +…/bot link in every User-Agent.
  2. The owner edits robots.txt. Page-level noindex (meta or X-Robots-Tag) takes effect on the next fetch of that page.
  3. The owner can check the result by looking for blocked:'robots' entries in the operator's audit log, or with the Robots tester.
  4. The opt-out applies to future fetches. Documents already indexed can be removed with DELETE /api/index/doc?url= or from the Index view.
